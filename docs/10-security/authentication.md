# Authentication

## Purpose

Defines who or what is permitted to interact with a running NOVA instance
at all, before any authorization or risk-tier question is even reached.

## Scope

Identity verification for the UI Layer, external API/SDK consumers, and
MCP/plugin connections. What an authenticated party is permitted to do is
`authorization.md`.

## OS-user-bound identity

NOVA's fundamental authentication boundary is the logged-in Windows user
session, per `docs/01-product/project-scope.md`'s single-user model —
NOVA operates only within the current OS user's session and does not
implement a separate NOVA-specific login layer for local, first-party UI
access. The UI Layer is authenticated implicitly by running within that
same OS session.

## External API/SDK authentication

External consumers of the REST/WebSocket API (`docs/08-api/rest-api.md`)
authenticate using a locally-issued token, generated by the running NOVA
instance and scoped to the current OS user session — this token is not
usable outside the local machine and is not a credential that grants any
access beyond what the issuing NOVA instance itself controls, consistent
with the no-hosted-backend, local-first scope
(`docs/00-overview/non-goals.md`).

## MCP and plugin authentication

Connections to external MCP servers use the credential configured for
that specific server (`secrets.md`), resolved from the OS credential
vault at connection time — NOVA authenticates itself *to* the MCP server
using that credential; this is separate from, and does not affect, how
NOVA authenticates callers *of* its own API.

## Shared-machine boundary

Per `docs/00-overview/non-goals.md`, each OS user account has an
independent NOVA workspace with no shared authentication or session
state between accounts — a token or session established under one OS
user's login is never valid for another OS user's NOVA workspace, even on
the same physical machine.

## Session persistence across reboot/sleep

Locally-issued tokens for external API consumers do not automatically
survive a NOVA restart; a consumer must re-authenticate after a restart,
which is a deliberate simplicity trade-off appropriate for a
single-machine, non-hosted product where the cost of re-authentication is
low and the alternative (persisting tokens across restarts) adds
complexity without a corresponding benefit at this scope.
