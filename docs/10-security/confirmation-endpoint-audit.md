# Nova Confirmation-Endpoint Security Audit

**Audit date:** 26 August 2026

**Repository:** `/home/ubuntu/Nova-test`
**Scope:** RuntimeApplication confirmation authority, canonical manager delegation, Electron main-process gateway validation, context-isolated preload forwarding, typed renderer contracts, renderer response projections, regression coverage, and repository verification.

## Executive conclusion

The audit enumerated every confirmation-bearing RuntimeApplication method and its desktop exposure. Before remediation, the confirmation predicates were generally present and fail-closed, but several Electron response paths violated Nova’s privacy boundary and one pair of task mutations bypassed the RuntimeApplication composition root. The audit remediated the validated findings in narrow, test-first commits. The current implementation keeps confirmation decisions at the RuntimeApplication or canonical execution boundary, validates boolean confirmation values at the gateway, rejects denied operations with the canonical `NOVA-SEC001` error, and projects renderer responses to bounded deterministic data.

The audit identified **ten validated security findings**. All ten are remediated in the current `main` branch. The current renderer contract no longer receives pairing channel credentials, plugin manifests or trust material, raw task records, workflow completed-node IDs, restored snapshot contents, outbound message bodies, prepared restore state, or setup inventory and configuration payloads. The audit also examined destructive desktop UI actions and classified them as a non-finding because the RuntimeApplication executor’s PermissionManager independently requires an approved confirmation status before non-read-only tool actions execute.

## Audit method and trust boundaries

The reviewed flow is renderer → preload → Electron `ipcMain` → authenticated named-pipe API Gateway → RuntimeApplication → canonical manager or executor. The renderer is treated as untrusted relative to privileged runtime state even though it is hosted by the application. Confirmation supplied by a UI is therefore not considered sufficient by itself; the authoritative runtime boundary must reject a false confirmation before downstream mutation or external effect.

The Electron window is created with `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true` in `apps/desktop/src/main/main.ts:560-571`. The preload exposes one `contextBridge.exposeInMainWorld("nova", novaApi)` call at `apps/desktop/src/preload/preload.ts:267`. `apps/desktop/test/preload-boundary.test.ts` asserts the exact public key order and the IPC invocation payloads, so the remediations preserved API ordering and changed only response shapes or payload fields where required.

## Confirmed non-findings and controls

The Electron window hardening and one-call context bridge prevent direct Node API exposure. The strict preload boundary test verifies exact bridge keys, order, and invocation payloads, including all confirmation arguments. The main gateway generally validates `typeof payload.confirmed === "boolean"` and converts failed Results into renderer-rejected errors; legacy envelope routes preserve their typed `Result` shape.

RuntimeApplication confirmation methods reject before manager delegation in the direct gate implementations. Delegated coordinator and assistant paths retain their own confirmation predicates, so callers that bypass the desktop gateway still encounter the canonical `NOVA-SEC001` behavior. Tests cover denied operations, unchanged state, and no downstream call for the principal manager families.

The destructive `desktop.ui-action` path was examined separately. The desktop main process prompts through `DesktopAgentController.confirmDestructiveUiAction` and only then sets the execution step’s confirmation status. This is not the authoritative protection by itself, but `RuntimeApplication.executeToolStep` delegates to `Executor`, whose `PermissionManager` rejects every non-read-only action unless `confirmation_status === "approved"` and the confirmation window is valid. The native controller also checks desktop-control permission, focused-window identity, action identifiers, and post-action accessibility evidence. The combined main-process prompt plus runtime PermissionManager gate is therefore a control, not an unresolved bypass.

Workspace locks, recovery locks, resource arbitration, and scheduler coordination were not treated as confirmation bypasses. They are internal concurrency and recovery mechanisms; their presence does not itself represent an external or irreversible user effect. Local model outputs, tool summaries, workflow checkpoint summaries, health projections, and device snapshots were checked as bounded projections and did not reveal raw provider payloads, filesystem paths, credentials, or internal execution context.

## Residual observations

The audit did not redesign unrelated read-only APIs. In particular, the renderer still has intentionally typed draft/input fields for composing email and channel messages, and read/draft APIs remain separate from confirmed send receipts. Those inputs originate in the renderer by product design; they are not privileged responses from the runtime. Configuration remains represented by the existing typed `NovaConfiguration` model, which carries vault references rather than plaintext provider credentials. Future work should continue replacing generic `unknown` fields in non-confirmation read APIs with explicit bounded schemas, but no remaining confirmed endpoint was found to return one of the prohibited sensitive payloads after the remediations above.
