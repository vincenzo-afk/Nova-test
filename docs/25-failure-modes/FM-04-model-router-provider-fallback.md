# FM-04: Model Router, Provider Layer, Fallback Engine & Capability Management

## Purpose

Everything that happens before a token is even generated: choosing which model/provider handles a request, what happens when that choice is wrong, unavailable, or fails, and how NOVA's capability registry can drift from reality.

## Failure Catalog

Each failure is assigned a stable ID (`FM-04-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-04-001** | Pick wrong model | Routing heuristic misclassifies task complexity/type (e.g. sends a reasoning-heavy task to a fast/cheap model). | Output quality score or downstream verifier failure rate spikes for a given routing decision. | Medium | Task-classification confidence gating: route to the higher-capability model whenever classification confidence is low. | Detect low-quality output via verifier and re-route the same request to a stronger model automatically. |
| **FM-04-002** | Use expensive model unnecessarily | Router defaults to the most capable model for simple tasks due to missing/broken classification. | Cost-per-request metric for simple task categories is abnormally high. | Low | Cheap-first routing with escalation only on verifier failure, not capability-first routing by default. | No user-facing recovery needed; correct the routing table and monitor cost trend. |
| **FM-04-003** | Choose weak model for a hard task | Same root cause as 001, opposite direction — under-provisioning capability for task complexity. | User correction rate or verifier failure rate for a task category spikes. | Medium | Same mitigation as 001: complexity-aware routing with confidence-gated escalation. | Escalate to the next capability tier automatically after a verifier failure, not just on the next unrelated request. |
| **FM-04-004** | Ignore local model when available | Router config not updated after a local model was installed/enabled, or hardware-detection cache is stale. | Local model sits idle (0 invocations) despite matching capability requirements and being marked available. | Low | Re-run hardware/model detection on its actual defined triggers (manual re-scan, new device added, or a local provider's `healthCheck()` pattern consistent with resource exhaustion), not only at first install, per `docs/18-providers/hardware-detection.md`'s Re-evaluation triggers section. | Refresh the capability registry and re-route subsequent matching requests to the local model. |
| **FM-04-005** | Wrong fallback order | Fallback list ordered by static preference, not live health/latency, sending traffic to a degraded provider before a healthy one. | Latency/error rate for the chosen fallback is worse than a lower-priority alternative that was skipped. | Medium | Health-aware dynamic fallback ordering, re-evaluated periodically against live provider status. | Manually or automatically reorder fallback list based on rolling health metrics; retry the request against the reordered list. |
| **FM-04-006** | Infinite fallback chain | Every provider in the fallback list fails and the chain has no terminal 'give up' state. | Fallback attempt count for a single request exceeds the provider list length without success. | High | Hard ceiling equal to fallback-list length; explicit terminal failure state with a user-facing message after exhaustion. | Surface an explicit 'all providers unavailable' error; do not silently retry beyond the list. |
| **FM-04-007** | Multiple fallbacks conflicting | Two fallback attempts fire concurrently due to a race in the failure-detection logic, producing two responses. | Two responses returned for one request ID. | Medium | Single-flight guarantee per request ID: only one fallback attempt in flight at a time. | Discard the duplicate response using request-ID deduplication; keep the first valid one. |
| **FM-04-008** | Fallback loses context | Provider switch mid-task drops conversation/context because the fallback provider's context format differs. | Fallback response ignores instructions/context that were present in the original prompt. | Medium | Provider-agnostic context serialization layer that every provider adapter must consume identically. | Re-inject the full context explicitly into the fallback provider's request rather than assuming it transferred. |
| **FM-04-009** | Fallback produces different output | Different model family/version produces a stylistically or factually different answer than the primary would have, surprising the user mid-conversation. | User flags inconsistency between two turns in the same conversation. | Low | Note in the response (or metadata) when a fallback model was used, so downstream consumers can account for the difference. | No rollback needed; log for routing quality review. |
| **FM-04-010** | Recovery impossible (fallback exhausted) | All configured providers, including local, are unavailable simultaneously. | Fallback chain fully exhausted with zero successful providers. | Critical | Maintain at least one offline/local capability tier as a last resort per `docs/18-providers/provider-routing.md`'s Offline Fallback section — the routing-priority guarantee lives there, not in `local-model-management.md`, per that document's own scope note. | Queue the request for retry when connectivity/provider health is restored; do not lose the user's request. |
| **FM-04-011** | Capability not discovered | New capability added to a provider but the registry sync job hasn't run, or failed silently. | Registry lookup returns 'unsupported' for a capability the provider actually supports. | Medium | Scheduled + event-triggered registry refresh, with alerting on sync-job failure. | Manually trigger a registry refresh; re-evaluate the blocked plan once the capability appears. |
| **FM-04-012** | Wrong capability selected | Two similarly-named capabilities exist (e.g. two different 'vision' variants) and the wrong one is matched. | Task fails at execution time with an interface mismatch despite passing capability lookup. | Medium | Namespaced, versioned capability IDs rather than fuzzy name matching. | Correct the capability mapping in the registry; re-run the specific failed step. |
| **FM-04-013** | Duplicate capability registration | Same capability registered twice (e.g. after a provider reconnect) creating ambiguous routing. | Registry lookup returns more than one match for a single capability ID. | Low | Idempotent registration keyed by provider+capability signature. | Deduplicate registry entries on next sync pass. |
| **FM-04-014** | Capability dependency missing | A capability declares it needs another capability (e.g. OCR needs image-decode) that isn't registered. | Dependency-graph validation at registry-load time finds an unresolved dependency. | Medium | Validate the full capability dependency graph at registration time, reject partial/broken registrations. | Block the dependent capability from being offered until its dependency is available; surface a clear diagnostic. |
| **FM-04-015** | Capability version mismatch | Router assumes capability schema v2 but provider only implements v1. | Schema validation failure on the request/response payload. | Medium | Version negotiation before invocation, comparing the router's required schema version against the provider's advertised `schema_version` (`docs/18-providers/provider-interface.md`'s Version negotiation section); router must check advertised version before use. | Downgrade the request to the version the provider actually supports, or route elsewhere. |
| **FM-04-016** | Capability disabled unexpectedly | Feature flag or admin action disables a capability mid-session without notifying in-flight tasks. | In-flight task fails referencing a capability that was available at plan time but not at execution time. | Medium | Re-validate capability availability immediately before execution, not only at plan time. | Replan the affected step using an alternative capability, or pause and notify the user. |
| **FM-04-017** | Capability permission mismatch | Capability requires a permission scope the current identity/session doesn't hold. | Authorization check fails at invocation despite capability lookup succeeding. | Medium | Fold permission scope into the capability-matching step itself, not a separate later check that can be forgotten. | Prompt for elevated permission via `docs/03-runtime/permission-manager.md`, or route to a capability that doesn't require it. |
| **FM-04-018** | Capability health degradation | Provider capability technically available but degraded (high latency, elevated error rate) without being marked unavailable. | Rolling error-rate/latency metrics for a capability cross a soft-degradation threshold. | Medium | Soft-degraded state distinct from hard-unavailable, feeding into fallback-ordering (see 005) before full failure occurs. | Deprioritize but don't fully exclude the degraded provider; monitor for recovery or full failure. |
| **FM-04-019** | Provider unavailable | Network partition, outage, or auth failure to the provider. | Connection/auth errors from the provider adapter. | High | Circuit breaker per provider to stop hammering a known-down provider. | Trip the circuit breaker, fall back per FM-04-005/006, retry with backoff once circuit resets. |
| **FM-04-020** | Wrong provider configuration | Config drift — endpoint, region, or model ID misconfigured after an update. | Requests fail with 4xx errors that indicate config problems, not transient failures. | Medium | Config validation/schema-check on load and on every config change, with a startup self-test per provider. | Roll back to the last known-good config; alert for manual review. |
| **FM-04-021** | Provider metadata outdated | Cached provider metadata (pricing, context limits, supported modalities) not refreshed after a provider-side change. | Request rejected by the provider for exceeding a limit the router believed was higher. | Low | TTL on cached provider metadata with periodic re-fetch. | Refresh metadata immediately on a limit-exceeded error and retry within the corrected limit. |
| **FM-04-022** | Wrong API endpoint | Regional or versioned endpoint misrouted (e.g. hitting a deprecated API version). | Deprecation warnings or unexpected schema in the response. | Low | Centralize endpoint configuration per provider+version, validated at build/deploy time. | Update endpoint config; no data loss expected if caught early. |
| **FM-04-023** | Billing disabled / quota exceeded | Provider account billing lapsed or quota exhausted. | 402/429-class errors from the provider. | High | Proactive quota/usage monitoring with alerts before hard limits are hit. | Fall back to an alternate provider/local model per the fallback engine; alert the account owner. |
| **FM-04-024** | Region restrictions | Provider/model not available in the user's configured region. | 403/451-class errors referencing region restriction. | Medium | Region-aware capability registry so restricted capabilities are never offered to ineligible sessions. | Route to a region-compliant alternative provider or capability. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- A wrong fallback order combined with a provider outage (FM-11) can route latency-sensitive requests to the slowest available model — fallback order must be re-validated whenever provider health changes, not fixed at startup only.
- Capability drift (registry says a model supports vision when the provider silently removed it) fails at the worst layer: mid-task, after the router already committed, rather than at plan-validation time — the capability registry needs periodic live re-verification, not just cached config.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
