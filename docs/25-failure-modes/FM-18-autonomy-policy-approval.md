# FM-18: Autonomous Decisions, Policy Engine & Human Approval

## Purpose

Governs the boundary between what NOVA does on its own and what it must ask permission for. Failures here directly determine whether the system is trustworthy for consequential actions.

## Scope & Related Documents

This file is part of `docs/25-failure-modes/`, the project-wide failure-mode catalog. It must be read alongside:

- `docs/23-autonomy/self-growing-capability.md` - `docs/23-autonomy/background-life-assistant.md` - `docs/23-autonomy/strategy-evaluation.md` - `docs/05-ai/escalation-rules.md` - `docs/23-autonomy/adaptive-personalization.md` - `docs/23-autonomy/automatic-software-installation.md` - `docs/23-autonomy/autonomous-plugin-discovery.md` - `docs/23-autonomy/goal-tracking.md`

## Failure Catalog

Each failure is assigned a stable ID (`FM-18-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-18-001** | Acts without approval | Action classified as low-consequence when it was actually high-consequence, or the classification itself was never run. | Post-hoc audit finds an executed action that should have required approval per policy but didn't go through the approval gate. | Critical | Default-deny: any action not explicitly classified as autonomous-safe requires approval, rather than default-allow with exceptions. | Attempt to undo/compensate the action if reversible (per failure-recovery.md); notify the user immediately regardless; fix the misclassification. |
| **FM-18-002** | Doesn't act when it should | Overly conservative policy blocks a genuinely low-risk, time-sensitive action, degrading usefulness. | User explicitly notes the system should have just acted; or a pattern of unnecessary approval requests for a specific low-risk action type. | Low | Periodically review approval-request patterns and recalibrate the policy to reduce unnecessary friction for consistently-approved low-risk categories. | Adjust the policy classification for that specific action type based on observed approval patterns. |
| **FM-18-003** | Wrong confidence estimate | Model's stated confidence about whether an action is safe to take autonomously doesn't match actual risk. | See FM-05-014; applied here specifically to the autonomy-decision confidence score. | Medium | Same as FM-05-014: calibrate against observed outcomes, don't trust self-reported confidence uncritically for consequential decisions. | Treat miscalibrated confidence as grounds to widen the approval-required scope for that decision category until recalibrated. |
| **FM-18-004** | Misjudged urgency | System either escalates a non-urgent matter as urgent (alert fatigue) or fails to escalate a genuinely urgent one. | User feedback or outcome analysis shows urgency classification didn't match actual stakes. | Medium | Explicit, reviewed urgency criteria per action category rather than an ad-hoc model judgment call each time. | Adjust urgency-classification criteria for the specific category based on the observed miss. |
| **FM-18-005** | Poor prioritization | Autonomous background tasks (per `docs/23-autonomy/background-life-assistant.md`) compete for resources/attention in a way that doesn't reflect actual user priority. | User has to manually reprioritize/cancel autonomous tasks frequently. | Low | Explicit, user-visible priority model for autonomous tasks, adjustable by the user, rather than an opaque internal ranking. | Surface the current autonomous-task queue and priority to the user; let explicit user feedback retrain the prioritization. |
| **FM-18-006** | Unsafe autonomous action | An action taken autonomously causes real-world harm (financial, data-loss, relationship) that a human would have caught. | Post-hoc incident review; ideally caught by a pre-action safety check rather than only after the fact. | Critical | Conservative default scope for autonomy — expand only for action categories with a track record of safe autonomous execution, per `docs/23-autonomy` and the Policy Engine. | Full incident response: undo/compensate if possible, notify the user, and treat as a mandatory input to narrowing autonomy scope going forward, not just a one-off bug fix. |
| **FM-18-007** | Wrong policy matched | Two policies could apply to an action and the wrong (less strict) one is selected. | Audit shows the applied policy doesn't match the most-specific/most-restrictive applicable rule. | High | Most-specific-and-most-restrictive-wins matching logic, not first-match or arbitrary priority ordering. | Reclassify and re-evaluate the action under the correct policy; treat as a gap in the policy-matching engine to fix, not just the one instance. |
| **FM-18-008** | Policy conflict | Two policies give contradictory verdicts for the same action with no defined precedence. | Policy engine returns ambiguous/contradictory results for a given action+context. | Medium | Explicit precedence ordering for all policies, validated for completeness (no unresolved conflicts) at policy-definition time. | Default to the more restrictive verdict when a conflict is detected at runtime, and flag the conflict for a precedence-ordering fix. |
| **FM-18-009** | Missing policy | No policy exists for a new action category (e.g. a newly added capability). | Policy lookup returns no match for an action type. | High | New capabilities cannot go live without an explicit corresponding policy entry — enforced as a release-checklist gate, per `docs/14-development/release-checklist.md`. | Default to requiring approval (safest default) for any action with no matching policy, until one is authored. |
| **FM-18-010** | Policy bypass | A code path invokes an action without going through the policy-check gate at all. | Static analysis / code audit finds an action-execution path with no policy-engine call in it. | Critical | Enforce policy checks at the single, unavoidable choke point for action execution (e.g. inside the Executor itself), not as an optional pre-check individual callers might skip. | Close the bypass path immediately; audit for other actions taken through the same unguarded path during the exposure window. |
| **FM-18-011** | Outdated rules | Policy hasn't been updated to reflect a changed risk profile (e.g. a capability that used to be low-risk is now higher-risk after a scope expansion). | Periodic policy review flags a rule whose underlying assumption (tied to a capability's current scope) has changed. | Medium | Tie policy review triggers to capability-scope changes, not just a calendar-based review cadence alone. | Update the policy immediately upon detecting the mismatch; retroactively review actions taken under the outdated rule if risk warrants it. |
| **FM-18-012** | Approval requested too late | Approval prompt surfaces after the action's window of relevance has passed, or after partial execution already occurred. | Approval timestamp is after the action's effective execution timestamp. | Critical | Approval must be a hard gate before any execution begins, structurally enforced (see FM-18-010), never a post-hoc notification mislabeled as approval. | Treat any post-hoc 'approval' as a bug, not a valid approval; if execution already occurred, follow FM-18-001's incident path. |
| **FM-18-013** | Approval never requested | See FM-18-001/010; called out separately as the specific failure of the request itself never firing. | Same detection as FM-18-001. | Critical | Same mitigation as FM-18-001/010. | Same recovery as FM-18-001. |
| **FM-18-014** | Duplicate approval dialogs | Same approval request surfaced to the user more than once due to a retry or a UI-state bug. | Two approval prompts for the same action ID. | Low | Idempotent approval-request creation keyed by action ID, same pattern as task deduplication (FM-02-010). | Deduplicate the dialog; if the user already responded to one, apply that response rather than prompting again. |
| **FM-18-015** | Wrong approval scope | Approval prompt describes the action too narrowly or too broadly relative to what will actually be executed. | User's granted approval doesn't match the actual executed action's full scope, found via post-execution audit. | High | Approval-prompt content must be generated from the exact same action specification that will be executed, not a separately-authored summary that can drift. | Treat any executed scope beyond what was approved as unauthorized (FM-18-001's incident path); fix the prompt-generation/execution-spec linkage. |
| **FM-18-016** | Timeout waiting for user | Approval request sits unanswered indefinitely, blocking the task with no resolution path. | Task remains in 'WaitingUser' state well beyond a reasonable response window. | Medium | Explicit timeout policy per action urgency tier — expire and either cancel or escalate, rather than waiting forever. | Cancel the action (safe default) or escalate per policy once timeout is reached; notify the user their action needs re-initiation if they still want it done. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- Every 'acts without approval' incident must be treated as a Policy Engine gap, not just an isolated agent misbehavior — if the action should not have happened autonomously, the policy that failed to catch it must be fixed, not just the specific agent instance patched.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
