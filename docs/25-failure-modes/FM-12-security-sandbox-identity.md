# FM-12: Security, Sandboxing & Identity Layer

## Purpose

The highest-severity category in this whole set — failures here tend to be silent until exploited, and the blast radius is rarely contained to a single task. Every entry here must be treated as a design constraint, not an edge case to patch later.

## Failure Catalog

Each failure is assigned a stable ID (`FM-12-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-12-001** | Secret leaked | Credential/API key logged in plaintext, included in a prompt sent to a model provider, or committed to a file NOVA writes. | Secret-scanning pass over logs/outputs/generated files detects a credential-shaped string. | Critical | Never pass raw secrets into model context; use reference tokens resolved only at the tool-execution boundary. Scan all logs and generated output before persistence. | Immediately rotate the leaked credential; scrub it from logs/storage; treat as a security incident with full audit trail per `docs/10-security/audit.md`. |
| **FM-12-002** | Prompt injection | See FM-06-013; included here as the security-layer's primary responsibility. | See FM-06-013. | Critical | Structural separation of instructions from untrusted data at every layer, per `docs/10-security/threat-model.md`. | See FM-06-013 mitigation/recovery; always log to the security audit trail. |
| **FM-12-003** | Tool injection | Malicious content manipulates which tool gets called or with what arguments, distinct from prompt injection targeting the model's text output. | Tool-call arguments contain content sourced from untrusted input that wasn't validated against the tool's schema/semantic constraints. | Critical | Validate tool arguments for semantic safety (not just schema shape) especially for high-consequence tools; never let untrusted content directly populate arguments for destructive/sensitive tools without a validation layer. | Block the call, log the attempted injection, review the source of the untrusted content. |
| **FM-12-004** | Privilege escalation | A lower-privilege context (plugin, sub-agent, user session) obtains capabilities beyond its granted scope. | Action executed that exceeds the acting context's declared permission scope, caught by a permission-boundary check. | Critical | Enforce least-privilege by default everywhere; every privilege boundary must be checked at the point of action, not assumed from earlier context, per `docs/10-security/permission-escalation.md`. | Revoke the improperly-obtained access immediately, audit what was done with it, and treat as an incident. |
| **FM-12-005** | Sandbox escape | Sandboxed code execution (FM-08 code gen, plugin execution) breaks out of its isolation boundary. | Sandbox integrity monitor detects access to resources outside the declared sandbox boundary. | Critical | Defense-in-depth sandboxing (OS-level isolation, not just language-level), per `docs/10-security/sandboxing.md`; never rely on a single isolation layer. | Kill the sandbox immediately, audit what it accessed before containment, treat as a critical incident. |
| **FM-12-006** | Data exfiltration | Sensitive data is sent to an unintended external destination (e.g. included in a tool call to an untrusted external service). | Data-flow monitoring flags sensitive-tagged content crossing a trust boundary to an external destination. | Critical | Data-loss-prevention checks on outbound calls that cross a trust boundary, especially for sensitive-tagged memory content. | Block the outbound call if caught before send; if not caught in time, notify affected parties per incident-response policy and rotate any exposed credentials. |
| **FM-12-007** | Unauthorized plugin | A plugin is installed/activated without going through the required review/consent flow. | Plugin activation event has no corresponding consent record. | High | Mandatory consent gate for plugin installation/activation, enforced at the plugin-lifecycle layer, not just presented in UI as a suggestion. | Deactivate the plugin, audit what it accessed while active, require explicit re-consent before reactivation. |
| **FM-12-008** | Wrong permission (general) | Permission granted at too broad a scope, or the wrong permission entirely, due to a UI/mapping bug. | Audit of granted-vs-actually-needed permissions for a capability shows over-grant. | Medium | Scope permission requests to the minimum needed per specific action, not a broad category, per `docs/10-security/permissions.md`. | Narrow the granted scope retroactively; re-prompt if the broader scope was actually needed for legitimate reasons. |
| **FM-12-009** | Wrong user identified (identity) | Multi-user device misattributes an action/memory to the wrong identity. | Action logged under an identity that doesn't match independent corroborating signals (device state, active session). | High | Strong identity verification (not just 'whoever is active') for any sensitive action or memory write, per `docs/10-security/authentication.md`. | Correct the attribution, audit what was exposed to/done as the wrong identity, apply FM-01-009's leak-response procedure if memory was involved. |
| **FM-12-010** | Cross-user memory leak | See FM-01-009; included here as the identity/security-layer's responsibility. | See FM-01-009. | Critical | See FM-01-009. | See FM-01-009. |
| **FM-12-011** | Identity conflict | Two identity records exist for what is actually the same person (or vice versa — one record spans two people). | Entity-resolution audit at the identity layer, analogous to FM-01-017 but for user identities specifically. | High | More conservative merge threshold for identity records than for general entity merges, given the higher stakes. | Split or merge per the specific case, preserving full audit trail of what was attributed to which identity when. |
| **FM-12-012** | Authentication desynchronization | Auth state differs between two components (e.g. UI thinks logged in, backend has expired the session). | One component's action fails with an auth error while another component reports the user as authenticated. | Medium | Single source of truth for auth state, propagated via events rather than each component maintaining independent state. | Force a re-sync of auth state across all components; re-authenticate if the source of truth itself has expired. |
| **FM-12-013** | Malicious plugin | A plugin behaves maliciously post-installation (either always was, or turned malicious via a compromised update). | Runtime behavior monitoring flags actions outside the plugin's declared capability manifest. | Critical | Sandboxed execution with a declared capability manifest, enforced at runtime — a plugin cannot silently do more than it declared, per `docs/16-extensibility/plugin-sandboxing.md`. | Immediately disable the plugin, audit its full action history, and treat as a security incident. |
| **FM-12-014** | Threat model gaps | A new attack surface (new feature, new integration) is shipped without updating the threat model. | Periodic threat-model review finds a component with no corresponding entry. | Medium | Threat-model review as a mandatory step in `docs/14-development/release-checklist.md` for any new capability surface. | Backfill the threat-model entry and run a targeted security review before the next release. |
| **FM-12-015** | Encryption failure | Data-at-rest or in-transit encryption misconfigured (wrong key, weak cipher, or accidentally disabled). | Encryption-configuration audit or a security scan flags unencrypted sensitive data. | Critical | Encryption-by-default for sensitive data categories with configuration validated at startup, per `docs/10-security/encryption.md`. | Re-encrypt affected data immediately; audit exposure window; rotate keys if compromise is plausible. |
| **FM-12-016** | Supply-chain compromise | A dependency (package, model weights, plugin) is compromised upstream. | Dependency integrity check (hash/signature verification) fails, or a known-vulnerable version is detected. | Critical | Pin dependencies with verified hashes/signatures; monitor vulnerability databases for installed dependency versions, per `docs/10-security/supply-chain-security.md`. | Pull the compromised dependency immediately, audit for any impact during the exposure window, patch/replace. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- Prompt injection (FM-06-013), sandbox escape, and privilege escalation form a kill chain: injected instructions attempt to escalate privilege, and a sandbox breach is what lets that escalation reach something real. Defense needs to work at every link, not just the first one.
- A permission system that's correct in the common case but has one silent bypass path is worse than a system with fewer features and no bypass — audit every permission-check call site for a path that skips it, not just the intended path.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
