# FM-06: Context Assembly, Prompt Construction & Session Management

## Purpose

Covers the machinery that turns retrieved memories, tool schemas, and conversation history into the actual prompt sent to a model, plus the session/conversation-state layer that spans multiple turns.

## Scope & Related Documents

This file is part of `docs/25-failure-modes/`, the project-wide failure-mode catalog. It must be read alongside:

- `docs/05-ai/context-builder.md` - `docs/05-ai/model-context-assembly.md` - `docs/05-ai/prompt-system.md` - `docs/05-ai/prompt-versioning.md`

## Failure Catalog

Each failure is assigned a stable ID (`FM-06-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-06-001** | Missing memories in context | Retrieval returned results but the context assembler's token budget dropped them before reaching the model. | Retrieved-but-unused memory count is nonzero in the assembly log for a response later found to be missing information. | Medium | Prioritize memories by importance score, not insertion order, when trimming to fit the token budget. | Re-assemble with the specific missing memory pinned as high-priority and regenerate. |
| **FM-06-002** | Too much context | Irrelevant context crowds out the token budget, diluting the model's attention on what matters. | Context-relevance score for included items is low on average for a given response. | Medium | Relevance-threshold filtering before assembly, not just a token-budget cutoff. | Trim to only high-relevance items and regenerate. |
| **FM-06-003** | Wrong ordering | Context items assembled in an order that de-emphasizes the most important facts (e.g. critical constraint buried in the middle). | Output ignores a fact that was present but poorly positioned in context. | Low | Place highest-priority context nearest the current query (recency-weighted positioning), per `docs/05-ai/context-builder.md`. | Reorder and regenerate. |
| **FM-06-004** | Duplicate context | Same fact included twice from two different retrieval sources without dedup. | Token-budget waste detected; same content hash appears twice in assembled context. | Low | Dedup assembled context items by content hash before finalizing the prompt. | No user-facing recovery needed; fix at the assembly stage. |
| **FM-06-005** | Context exceeds model limit | Assembled context exceeds the target model's actual context window. | Provider returns a context-length error, or the request is silently truncated by the provider. | High | Enforce a token-budget check against the specific target model's limit before sending, with a safety margin. | Trim per FM-06-002's prioritization and retry within budget. |
| **FM-06-006** | Sensitive information included accidentally | A memory scoped as sensitive (health, financial) is included in context for a task that doesn't need it. | Sensitivity-tag audit on assembled context flags an item whose scope doesn't match the task's declared purpose. | Critical | Purpose-based filtering: sensitive-tagged memories only enter context when the task's declared purpose explicitly requires that category, per `docs/05-ai/context-builder.md`'s Sensitive-category purpose gate section. | Strip the item, regenerate, and log to `docs/10-security/audit.md` even if no external leak occurred. |
| **FM-06-007** | Important facts omitted | Same as 001 but caused by a retrieval gap rather than a budget-trimming gap — included here as the assembly-layer's responsibility to detect, not just accept upstream retrieval as ground truth. | Downstream verifier or user flags a materially incomplete answer. | Medium | Assembly layer must sanity-check retrieval count/coverage against task type (e.g. a 'what do you know about X' task with zero retrieved memories about X is suspicious). | Trigger a broader/secondary retrieval pass before finalizing the prompt. |
| **FM-06-008** | Context poisoning | Adversarial or corrupted content in a retrieved document/memory injects instructions the model then follows. | Assembled context contains imperative-style text ('ignore previous instructions...') inside what should be inert reference material. | Critical | Structurally separate untrusted retrieved content from instructions in the prompt (e.g. explicit delimiters, treating retrieved text as data-only), per `docs/10-security/threat-model.md`. | Strip/quarantine the offending source from future retrieval until reviewed; treat as a security incident, not just a quality bug. |
| **FM-06-009** | Broken template | Prompt template has a syntax error or a logic bug introduced by an edit. | Template render step throws or produces malformed output. | High | Version and test prompt templates like code, with CI validation per `docs/05-ai/prompt-versioning.md`. | Roll back to the last known-good template version. |
| **FM-06-010** | Missing variables | Template expects a variable the caller didn't supply. | Render-time error or a literal placeholder string leaking into the final prompt. | Medium | Schema-validate template inputs before render; fail loudly rather than rendering with a gap. | Fix the caller to supply the missing variable; do not send a partially-rendered prompt to the model. |
| **FM-06-011** | Placeholder not replaced | Template renders successfully but a placeholder token slips through into the actual prompt/output due to a bug. | Output or logged prompt contains a literal '{{...}}'-style token. | Medium | Post-render lint that scans for unreplaced placeholder syntax before the prompt is sent. | Block the send, fix the template bug, retry. |
| **FM-06-012** | Invalid system prompt | System prompt assembly step produces something that violates the model provider's required format. | Provider rejects the request with a format error. | Medium | Validate system-prompt structure against each provider's specific requirements before send. | Fall back to a provider-compliant minimal system prompt and retry. |
| **FM-06-013** | Prompt injection | User input or retrieved content contains instructions designed to override system-level behavior. | Output exhibits behavior inconsistent with system-level constraints, correlated with suspicious phrasing in the input. | Critical | Treat all user/external input as data, never as instructions with system-level authority, per `docs/10-security/threat-model.md`; keep privilege boundaries between system and user content explicit. | Refuse the affected action if it would violate a system-level constraint; log the attempt for security review. |
| **FM-06-014** | Contradictory instructions | System prompt and a dynamically-injected instruction (e.g. from a plugin) conflict. | Output is inconsistent because the model resolved the conflict arbitrarily. | Medium | Explicit precedence rules for instruction sources (system > user > plugin > retrieved content), documented and enforced at assembly time. | Re-assemble applying the precedence rule explicitly and regenerate. |
| **FM-06-015** | Wrong role assignment | Content intended as 'assistant' history is assembled as 'user' role or vice versa, confusing the model about who said what. | Model responds as if the user said something the assistant actually said. | Medium | Strict role-tagging validation at assembly time, unit-tested against the conversation-history schema. | Fix the role mapping bug and regenerate the current turn. |
| **FM-06-016** | Session corruption | Session state file/record damaged by a crash or malformed write. | Session load fails deserialization or returns partial state. | High | Same WAL/checksum pattern as memory storage (FM-01-005) applied to session state. | Restore from last valid checkpoint; if unrecoverable, start a fresh session and offer to re-link prior context if found. |
| **FM-06-017** | Lost conversation | Session reference dropped (e.g. UI navigates away, ID not persisted) before it was durably saved. | Session ID referenced by the client has no server-side record. | Medium | Persist session state on every turn, not just on explicit close/save. | Reconstruct from event log if available; otherwise treat as data loss and inform the user rather than silently starting blank. |
| **FM-06-018** | Wrong session loaded | Session-lookup bug loads a different (possibly another user's) session due to an ID collision or caching bug. | Content in the loaded session doesn't match the expected user/identity. | Critical | Session IDs must be scoped to identity and validated on every load, not just looked up by a bare session ID. | Immediately terminate the load, treat as a potential privacy incident (cross-reference FM-01-009), and log per `docs/10-security/audit.md`. |
| **FM-06-019** | Session expiration (mishandled) | Session times out mid-task, losing in-progress state the user expected to persist. | User returns to an in-progress task and finds it reset. | Medium | Distinguish 'idle conversation timeout' from 'in-progress task state', which must survive independently of session TTL. | Resume the in-progress task from its Task Manager checkpoint even if the chat session itself expired. |
| **FM-06-020** | Duplicate sessions | Two session records created for what the user experiences as one continuous conversation (e.g. across device reconnect). | Two active session IDs referencing overlapping timeframes for the same identity. | Low | Reconnect logic must resume an existing session rather than always creating a new one. | Merge session histories chronologically; keep one canonical session going forward. |
| **FM-06-021** | Session merge conflicts | Attempting to merge two sessions (e.g. after 020) produces an inconsistent combined history. | Merged session has out-of-order or duplicated turns. | Low | Deterministic merge by timestamp with dedup by turn content-hash. | Manual/automated cleanup pass on the merged session; worst case, keep both as separate but linked sessions rather than a broken merge. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- Context assembly failures and prompt construction failures are adjacent stages in the same pipeline — a broken template (FM-06-006) often only becomes visible as a downstream hallucination (FM-05-001), so trace prompt-quality issues backward through this whole chain before assuming the model itself is at fault.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
