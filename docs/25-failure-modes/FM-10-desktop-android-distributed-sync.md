# FM-10: Desktop Automation, Android, Distributed Devices & Sync

## Purpose

NOVA spans desktop, Android, and cloud runtimes. This file covers both the single-device automation risks (clicking the wrong thing on a real OS) and the multi-device distributed-systems risks that only appear once more than one NOVA instance shares state.

## Failure Catalog

Each failure is assigned a stable ID (`FM-10-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-10-001** | Click wrong button (desktop) | Stale screenshot, or two visually-similar buttons at different coordinates. | Post-click system state doesn't match expected effect. | High | Re-verify target element identity (not just coordinates) immediately before clicking. | Detect via unexpected state, attempt undo if the action was destructive, and retry against the correct target. |
| **FM-10-002** | Close wrong app | Window-matching logic selects the wrong instance among multiple open windows of similar apps. | Expected app is still open, or an unintended app closed. | High | Match by window title + process ID, not just app name, when multiple instances can exist. | Reopen the closed app if state can be recovered; log the matching bug. |
| **FM-10-003** | Delete wrong file | Path resolution or wildcard matching selects more/different files than intended. | File deletion audit log shows a broader deletion scope than what was requested. | Critical | Confirm the exact resolved file list with the user (or a dry-run diff) before any destructive multi-file operation. | Restore from backup/trash per `docs/13-devops/backup.md`; treat as a critical incident requiring root-cause review before the same automation pattern runs again. |
| **FM-10-004** | Wrong window focused | OS focus changed by an unrelated event (notification, user interaction) between planning the action and executing it. | Action's effect appears in a different window than intended. | Medium | Re-verify focused window immediately before the action, not just at the start of the task. | Re-focus the correct window and retry. |
| **FM-10-005** | Wrong monitor | Multi-monitor coordinate calculation uses the wrong monitor's origin. | Click/action lands on the wrong physical display. | Medium | Explicitly resolve monitor context per action rather than assuming a single implicit primary display. | Recompute coordinates against the correct monitor and retry. |
| **FM-10-006** | Drag incorrectly | Drag-and-drop start/end points miscalculated, especially across window boundaries. | Dropped item doesn't land in the expected target location. | Medium | Verify both start and end element identity, not just coordinates, before and after the drag. | Undo if possible (move item back); retry with corrected coordinates. |
| **FM-10-007** | Wrong shortcut | Keyboard shortcut sent doesn't match the target app's actual bindings (app-specific or OS-version-specific differences). | Observed effect doesn't match the shortcut's expected action. | Low | Prefer explicit menu/command invocation over shortcuts where reliability matters more than speed. | Fall back to menu-based invocation of the same command. |
| **FM-10-008** | Accessibility failure | Target app doesn't expose an accessibility tree, forcing pure-vision automation with lower reliability. | Accessibility API returns empty/minimal tree for the target app. | Medium | Detect low/no accessibility support early and switch automation strategy (vision-first) rather than failing repeatedly against an empty tree. | Fall back to vision-based automation for that specific app going forward. |
| **FM-10-009** | Permission revoked (Android) | User revokes a permission NOVA's companion app depended on, mid-session. | Android API call for that permission returns a security exception. | Medium | Check permission status before each sensitive action, not only at app install/first-run. | Prompt the user to re-grant, with clear context on why it's needed; degrade gracefully (skip that specific capability) if declined. |
| **FM-10-010** | Device offline (Android) | Companion device loses connectivity to the coordinating NOVA instance. | Heartbeat from the Android companion stops. | Medium | Queue actions locally on the companion with sync-on-reconnect rather than failing outright. | Sync queued actions once connectivity resumes; deduplicate against any actions that also happened via another path meanwhile. |
| **FM-10-011** | Notification inaccessible | OS notification-access permission not granted, or a specific app's notifications are excluded by OS policy. | Expected notification-derived event never arrives. | Low | Detect at setup time whether notification access is actually functional for the target app category, not just permission-granted. | Surface a clear setup gap to the user rather than silently missing events indefinitely. |
| **FM-10-012** | App update changed UI (Android) | Target app updates and changes its layout, breaking prior automation patterns. | Previously-working interaction pattern starts failing consistently after a detected app version change. | Medium | Detect app version changes and treat as a trigger to re-validate cached interaction patterns for that app. | Fall back to vision-based interaction until the pattern is re-learned/updated. |
| **FM-10-013** | Background restrictions (Android) | OS aggressively kills or throttles the background companion process to save battery. | Companion process liveness check fails despite the device being online. | Medium | Request appropriate background-execution exemptions where legitimately needed, and design for graceful resume rather than assuming continuous background execution. | Resume pending work on next foreground/wake event; don't assume lost background time equals lost work. |
| **FM-10-014** | Screen locked (Android/desktop) | Device locks mid-automation, interrupting the interaction sequence. | Action fails because the target surface is no longer visible/interactable. | Medium | Detect lock state before attempting UI automation; queue and resume rather than failing hard. | Wait for unlock (with a bounded timeout) or defer the task, then resume from the last completed step. |
| **FM-10-015** | Different Android version | API/behavior difference across Android versions breaks an assumption made for one specific version. | Feature/permission behaves differently than expected on a specific OS version. | Low | Version-gate automation strategies explicitly rather than assuming one implementation works everywhere. | Maintain version-specific fallback paths for the affected interaction. |
| **FM-10-016** | Network partition (distributed) | Two or more NOVA instances can't reach each other or the sync backend. | Sync heartbeat/connectivity check fails between instances. | High | Design every cross-device feature to degrade gracefully to single-device operation during a partition, per `docs/20-devices/multi-device-architecture.md`. | Reconcile state once connectivity is restored using the same conflict-resolution logic as FM-10-023. |
| **FM-10-017** | Split-brain state | Two instances both believe they are the authoritative source of truth during/after a partition. | Two divergent state histories exist for what should be one canonical timeline. | Critical | Single elected coordinator (or CRDT-based merge with no single-writer assumption) rather than allowing two instances to both assume authority. | Merge divergent histories using the conflict-resolution policy; surface unresolvable conflicts to the user rather than silently picking one side. |
| **FM-10-018** | Conflicting updates | Same memory/task edited on two devices before sync completes. | Sync detects two versions of the same record with a common ancestor but divergent edits. | Medium | Version vectors / last-write-wins-with-audit-trail per record, not whole-database overwrite. | Apply conflict resolution per field where possible; surface irreconcilable conflicts to the user. |
| **FM-10-019** | Duplicate execution across devices | Same task executed independently on two devices because coordination state wasn't synced before both started. | Two completed-task records for the same task ID/goal. | Medium | Distributed lock or single-coordinator assignment for task execution, not opportunistic execution by whichever device notices first. | Keep the first-completed result; discard/rollback the duplicate if it had side effects, using compensation (see failure-recovery.md). |
| **FM-10-020** | Lost synchronization | Sync process silently stops (crashed, misconfigured) without alerting. | Sync-lag metric grows unbounded with no corresponding error surfaced. | Medium | Active sync-health monitoring with alerting on lag threshold, not just relying on absence-of-errors as a health signal. | Restart the sync process and reconcile the backlog; audit for any conflicts accumulated during the outage. |
| **FM-10-021** | Clock skew (distributed) | Devices' clocks disagree, corrupting timestamp-based ordering of synced events. | Event ordering inferred from timestamps contradicts causally-known ordering (e.g. a 'reply' timestamped before its 'original'). | Medium | Use logical/vector clocks or server-authoritative timestamps for ordering-sensitive sync, not raw device local time, per `docs/00-overview/time-semantics.md`. | Re-order using logical causality instead of raw timestamps where they conflict. |
| **FM-10-022** | Partial replication | Only some memory/state categories synced successfully before a failure, leaving devices inconsistent in specific areas. | Spot-check comparison between devices shows category-specific divergence. | Medium | Track sync completeness per category/shard, not just a single global 'synced' boolean. | Resume replication targeted at the specific incomplete categories, not a full resync. |
| **FM-10-023** | Eventual consistency violations | A read on one device observes a state that will later be proven inconsistent with the eventual merged state, causing a decision based on stale info. | Downstream action taken on device A contradicts state that later arrives from device B. | Medium | Where correctness matters (e.g. don't double-book), require read-after-write consistency via the coordinator rather than trusting local eventually-consistent state. | Detect the contradiction on merge and apply compensation for any action taken on the stale read. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- Split-brain state (FM-10-023) is the multi-device analogue of the single-agent race condition in FM-03 — same root cause (concurrent writers, no single source of truth), different scale. Solve both with the same conflict-resolution primitive rather than two bespoke fixes.
- Desktop automation acting on the wrong window and Android's screen-lock interruption are both instances of 'automation acted on stale UI state' — always re-verify the target surface immediately before acting, never trust a capture from even one step earlier.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
