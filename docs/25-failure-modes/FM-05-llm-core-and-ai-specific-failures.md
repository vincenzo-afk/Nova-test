# FM-05: LLM Core Behavior & AI-Specific Failure Modes

## Purpose

Failures intrinsic to the model itself, independent of routing or infrastructure: hallucination, instruction-following breakdowns, and the slow, hard-to-detect 'drift' failures unique to long-running intelligent systems.

## Scope & Related Documents

This file is part of `docs/25-failure-modes/`, the project-wide failure-mode catalog. It must be read alongside:

- `docs/05-ai/hallucination-prevention.md` - `docs/05-ai/explainability.md` - `docs/05-ai/confidence-propagation.md` - `docs/05-ai/reasoning-engine.md` - `docs/05-ai/deterministic-first.md` - `docs/05-ai/ambiguity-resolution.md` - `docs/05-ai/decision-and-confidence-contracts.md` - `docs/05-ai/verification-and-stop-conditions.md` - `docs/05-ai/episodic-replay.md`

## Failure Catalog

Each failure is assigned a stable ID (`FM-05-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-05-001** | Hallucinate | Model fills a knowledge/context gap with plausible-sounding fabricated content. | Citation-grounding check finds claims with no supporting retrieved source; or fact-check against known state fails. | High | Ground every factual claim in retrieved context; require explicit 'I don't know' when grounding fails, per `docs/05-ai/hallucination-prevention.md`. | Flag response as ungrounded before delivery; regenerate with stricter grounding constraints or surface uncertainty to the user. |
| **FM-05-002** | Ignore instructions | Model deprioritizes a system/developer instruction in favor of user request framing, or long context dilutes earlier instructions. | Output violates an explicit constraint stated in the system prompt. | Medium | Reassert critical constraints near the end of the prompt (recency bias), and validate output against constraints post-generation. | Regenerate with the violated constraint restated and highlighted; if repeated, escalate to a stronger model. |
| **FM-05-003** | Produce invalid JSON/code | Model breaks structured-output format under complex or long generations. | Schema validation fails on parse. | Medium | Constrained decoding / structured-output mode where the provider supports it; otherwise schema-validate and auto-repair on failure. | Retry with explicit schema restated; fall back to a smaller/simpler extraction task if retries fail. |
| **FM-05-004** | Forget context (LLM) | Effective context window exceeded or attention degrades over very long contexts ('lost in the middle'). | Model contradicts or fails to use information present earlier in the same context. | Medium | Summarize/compress older context and keep critical facts near the prompt boundary per `docs/05-ai/context-builder.md`. | Re-inject the forgotten fact explicitly close to the current turn and regenerate. |
| **FM-05-005** | Misunderstand request | Ambiguous phrasing resolved incorrectly, or a domain-specific term interpreted with its general meaning. | Verifier or user correction indicates output doesn't match intent. | Medium | Ambiguity detection with clarifying-question fallback per `docs/05-ai/ambiguity-resolution.md` rather than guessing silently. | Ask a targeted clarifying question rather than re-guessing blindly on retry. |
| **FM-05-006** | Over-answer / under-answer | Model provides far more or far less detail than the task warrants, ignoring implicit scope cues. | Response length/detail heuristic falls outside the expected band for the task type. | Low | Task-type-aware response-length guidance in the prompt template (`docs/05-ai/prompt-system.md`). | No system-level recovery needed beyond prompt-template correction; monitor via feedback. |
| **FM-05-007** | Fabricate APIs / fabricate files | Model references a function, library, or file path that doesn't exist, especially for less-common libraries. | Static validation of referenced imports/paths against the actual filesystem/package registry fails. | High | Ground code generation against actual project structure and verified package registries, not memory alone. | Reject the generation at the compile/lint stage (see FM-08); regenerate with the real API surface provided in context. |
| **FM-05-008** | Goal drift | Over a long multi-step task, small reinterpretations compound until the system is solving a subtly different problem than requested. | Periodic goal-alignment check compares current plan state against the original goal statement and finds material divergence. | High | Re-anchor to the original, verbatim goal statement at each replanning checkpoint, not just at task start, per `docs/03-runtime/planner.md`'s Goal-drift prevention (re-anchoring) section. | Halt, surface the drift explicitly to the user/verifier, and realign before continuing rather than completing the drifted task. |
| **FM-05-009** | Plan drift | Plan is silently modified mid-execution (e.g. by a replanning step) without re-validating against the original acceptance criteria. | Final plan's step list, diffed against the initially validated plan, shows unexplained divergence. | Medium | Any replan must re-pass the same validation gate the original plan passed, not skip validation as an 'update'. | Re-validate the drifted plan against acceptance criteria; reject and revert if it fails. |
| **FM-05-010** | Context drift | Working memory accumulates stale or superseded facts across a long session without pruning. | Response references outdated state that was corrected earlier in the same session. | Medium | Active context pruning: superseded facts are marked and deprioritized, not just appended forever. | Prune stale context and regenerate the affected response. |
| **FM-05-011** | Memory drift | See also FM-01 — model's summarized memory of a long interaction diverges from what actually happened. | Summary-vs-transcript spot check disagrees on a material fact. | Medium | Periodic re-grounding of the working summary against the raw event log, not summary-of-summary chaining indefinitely. | Regenerate the summary from raw events rather than compounding the drifted summary further. |
| **FM-05-012** | Preference drift | Model's model of user preference shifts based on a small number of recent, possibly atypical interactions. | Recommendation/personalization output contradicts an established, high-confidence preference. | Low | Weight long-established preferences more heavily than a small number of recent signals; require a consistency threshold before updating a preference. | Revert to the prior, higher-confidence preference model; treat the contradicting signal as a data point, not an override. |
| **FM-05-013** | Agent disagreement | See also FM-03 — covered here for the case of a single model reasoning with itself across multiple passes (self-consistency) and getting different answers. | Multiple sampled reasoning paths for the same question converge to different answers. | Medium | Self-consistency voting or a designated arbitration pass for high-stakes single-model decisions. | Surface the disagreement and confidence spread rather than picking one path arbitrarily and hiding the uncertainty. |
| **FM-05-014** | Confidence miscalibration | Model expresses high certainty on a low-accuracy claim, or hedges excessively on a high-accuracy one. | Stated confidence doesn't correlate with verifier pass/fail rate over a sample window. | Medium | Calibrate confidence language against actual observed accuracy per `docs/05-ai/confidence-propagation.md`; don't trust the model's self-reported confidence uncritically. | Downstream systems must treat stated confidence as a weak signal until recalibrated, not a strong one. |
| **FM-05-015** | Hallucinated state | Model believes a prior action succeeded (e.g. 'I created the file') when it didn't actually execute, due to reasoning about the action rather than its real result. | Actual system state (file doesn't exist) contradicts the model's claimed state. | Critical | Never let the model assert task state from reasoning alone — every state claim must be grounded in an actual tool-execution result. | Re-verify actual system state before reporting to the user; correct the false claim immediately. |
| **FM-05-016** | False success reporting | Task marked complete based on the model's own narrative of success rather than an independent verification step. | Verifier, run independently of the completing agent, finds the goal unmet despite a 'success' report. | Critical | Verification must be structurally independent of the agent that performed the work — never let an agent grade its own homework as the sole gate. | Reopen the task as Unverified/Failed; never let a self-reported success bypass independent verification. |
| **FM-05-017** | Tool overconfidence | Model calls a tool with parameters it isn't actually sure are correct, presenting the call as certain. | Tool call fails validation, or produces a result inconsistent with what a correct call would produce. | Medium | Require explicit confidence/uncertainty signaling before tool invocation for high-consequence tools (write, delete, send). | Route low-confidence tool calls through human approval (FM-18) before execution. |
| **FM-05-018** | Premature task completion | Model stops after a partial result, believing the task's scope was smaller than actually requested. | Verifier compares delivered scope against full acceptance criteria and finds gaps. | Medium | Explicit scope checklist derived from the goal, checked item-by-item before marking complete. | Resume the task against the remaining checklist items rather than treating it as a new task. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- Goal drift and plan drift are the same failure observed at different timescales — a system that checks plan-vs-goal alignment only once at task start will miss drift that accumulates over a long-running task; re-check periodically, not just at t=0.
- False success reporting is the most dangerous failure in this category because it defeats every downstream safety net that assumes failures are visible — treat unverified success as a distinct state from verified success everywhere in the system, never collapse the two.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
