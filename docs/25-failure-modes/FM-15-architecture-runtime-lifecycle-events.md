# FM-15: Architecture, Runtime Lifecycle, State Machine & Event System

## Purpose

The structural failures underneath everything else: how NOVA's services start up, stay up, transition between states, and communicate via events. These failures are often invisible until they cause a failure in a 'higher' subsystem, so root-cause analysis should always check this layer when a bug seems to defy its apparent subsystem's logic.

## Failure Catalog

Each failure is assigned a stable ID (`FM-15-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-15-001** | Component initialization order | Service B starts before its dependency Service A is ready. | Service B's first calls to Service A fail with 'not ready' rather than a clean startup. | High | Explicit dependency graph for startup order, enforced by the runtime manager, not implicit ordering by launch script sequence. | Restart Service B after confirming Service A's readiness; fix the dependency declaration. |
| **FM-15-002** | Dependency injection failures | A required dependency isn't registered/available at the point a component requests it. | DI container throws a resolution error at construction time. | Medium | Validate the full DI graph at startup (fail fast) rather than discovering missing dependencies lazily at first use. | Fix the registration; this should be caught in CI before it ever reaches runtime. |
| **FM-15-003** | Circular service dependencies | Service A depends on Service B which depends on Service A. | DI/startup graph analysis detects a cycle. | High | Reject circular dependencies at build/startup-validation time; require an explicit event-based decoupling for any genuinely mutual relationship. | Refactor to break the cycle (e.g. introduce an event or a shared lower-level service) rather than working around it at runtime. |
| **FM-15-004** | Configuration drift | Running configuration differs from the intended/declared configuration due to an untracked manual change. | Config-audit compares live config against the source-of-truth declaration and finds a diff. | Medium | Configuration-as-code with drift detection, per `docs/14-development/configuration.md` and `configuration-schema.md`. | Reconcile by reapplying the declared configuration, or formally update the declaration if the manual change was intentional. |
| **FM-15-005** | Module version incompatibility | Two internal modules built against incompatible shared-interface versions. | Interface-compatibility check fails at load/link time, or a subtle runtime mismatch occurs. | Medium | Semantic versioning enforced on internal module interfaces with compatibility checks in CI, per `docs/14-development/module-contract-standard.md`. | Roll back the incompatible module version until both sides are compatible again. |
| **FM-15-006** | Runtime plugin incompatibility | Plugin built against an older/newer NOVA API version than currently running. | Plugin load fails an API-version compatibility check. | Medium | Plugin manifest declares required NOVA API version range, checked at load time, per `docs/16-extensibility/plugin-architecture.md`'s `nova_api_version_range` manifest field. | Block incompatible plugin load with a clear message rather than allowing a partial/broken load. |
| **FM-15-007** | Feature flag conflicts | Two feature flags interact in an untested combination, or a flag's dependency on another flag isn't enforced. | Unexpected behavior traced to a specific flag combination not covered by test matrix. | Low | Declare flag dependencies/exclusions explicitly; test at least the common combinations, per `docs/14-development/feature-flags.md`. | Disable the conflicting combination; add it to the test matrix going forward. |
| **FM-15-008** | Startup race conditions | Two components racing to initialize a shared resource (e.g. both trying to create the same DB table). | Intermittent startup failures that don't reproduce consistently. | High | Idempotent initialization operations, or a single designated owner for any shared-resource initialization. | Add explicit coordination (lock or ordering) for the specific racing operation. |
| **FM-15-009** | Partial initialization | A component reports 'started' before all of its internal setup actually completed. | Component accepts requests that fail because an internal dependency wasn't actually ready. | High | Readiness must mean fully-initialized, checked via an explicit readiness probe distinct from liveness, per `docs/03-runtime/service-lifecycle.md`. | Don't route traffic to a component until its readiness probe passes, not just its liveness probe. |
| **FM-15-010** | Graceful shutdown failures | Component doesn't finish in-flight work or persist state before being killed. | Data loss or inconsistent state observed after a restart following a shutdown. | High | Shutdown hooks with a bounded grace period to complete/checkpoint in-flight work before hard-kill. | Recover in-flight work from the last checkpoint on next startup; investigate why graceful shutdown didn't complete in time. |
| **FM-15-011** | Startup failure | Service fails to start entirely (bad config, missing dependency, port conflict). | Process exits immediately or fails health check indefinitely. | Critical | Fail-fast with a clear, specific error message rather than a generic crash; validate all preconditions before attempting to bind/serve. | Fix the specific blocking issue identified in the startup error; do not silently retry a startup that will deterministically fail again. |
| **FM-15-012** | Shutdown interrupted | Shutdown sequence itself is interrupted (e.g. by a forced kill signal) before cleanup completes. | Resources (locks, temp files, connections) left in an inconsistent state after the process is gone. | Medium | Design cleanup to be resumable/idempotent on next startup rather than assuming shutdown always completes. | Run a startup-time cleanup pass that reconciles any resources left behind by an interrupted shutdown. |
| **FM-15-013** | Restart loop | Service crashes immediately after each restart, looping indefinitely (crash loop). | Restart count for a service exceeds a threshold within a time window. | Critical | Circuit breaker on restarts: after N failures in a window, stop auto-restarting and surface for manual intervention rather than looping forever. | Halt the restart loop, surface the underlying crash reason clearly, require explicit intervention before further auto-restart attempts. |
| **FM-15-014** | Hot reload inconsistency | Live code/config reload leaves some in-memory state referencing the old version and some the new. | Mixed old/new behavior observed within the same running process after a reload. | Medium | Prefer full restart over hot reload for state-sensitive components; where hot reload is used, version-tag in-memory state to detect mixing. | Force a full restart if inconsistency is detected rather than trying to reconcile mixed state live. |
| **FM-15-015** | State lost after restart | In-memory state that should have been persisted wasn't, and is gone after restart. | Comparison of pre-restart and post-restart state shows an unexpected gap. | High | Explicit persistence contract: any state that must survive restart must be written durably, not just held in memory, verified via restart tests. | Reconstruct from the durable source (event log, checkpoint) if possible; otherwise this is data loss requiring a fix to the persistence contract. |
| **FM-15-016** | Resource cleanup failure | File handles, connections, or locks not released on component teardown. | Resource-leak monitoring shows growth in open handles/connections correlated with component restarts. | Medium | Use structured resource-management patterns (context managers / RAII-equivalent) that guarantee cleanup even on error paths. | Restart the affected component to force OS-level cleanup as a stopgap; fix the specific leak. |
| **FM-15-017** | Zombie processes / orphan workers | Child process/worker outlives its parent and is never reaped, or continues doing stale work. | Process list shows workers with no live parent/coordinator reference. | Medium | Process supervision with explicit parent-child lifecycle binding; workers must self-terminate if they lose contact with their coordinator. | Terminate orphaned processes; add/verify the self-termination-on-orphan-detection logic. |
| **FM-15-018** | Capability disabled unexpectedly (runtime) | Cross-ref FM-04-016 — included here as a runtime-lifecycle event that a running task needs to react to. | See FM-04-016. | Medium | See FM-04-016. | See FM-04-016. |
| **FM-15-019** | Invalid state transition | State machine attempts a transition not allowed from the current state (e.g. 'complete' directly from 'not started'). | Transition-validation guard rejects the attempted transition. | Medium | Explicit, exhaustive state-transition table validated at every transition attempt, not just the common paths. | Reject the invalid transition; investigate what upstream logic attempted it, since it indicates a bug in the caller. |
| **FM-15-020** | Dead state | A state exists in the machine that has no valid outgoing transition, trapping any entity that reaches it. | Entities accumulate in a specific state with no further transitions ever observed. | Medium | State-machine design review to guarantee every non-terminal state has at least one valid exit path. | Add the missing transition, or reclassify the state as an intentional terminal state if that was the actual design intent. |
| **FM-15-021** | Infinite state loop | Cycle of states with no terminal condition (A → B → A → B ...). | Transition-count-per-entity exceeds a sane ceiling. | High | Cycle detection in the state-machine definition itself, rejected at design/validation time. | Force-terminate the looping entity into a designated error/manual-review state. |
| **FM-15-022** | Unknown state | An entity is found in a state that isn't defined in the current state-machine schema (e.g. after a schema change without migration). | State-value lookup against the current schema fails. | Medium | Version the state-machine schema and migrate existing entities' state on schema change, not just new entities. | Map the unknown state to the closest valid equivalent, or route to manual review if no safe mapping exists. |
| **FM-15-023** | State rollback failure | Attempted rollback to a prior state fails partway, leaving an inconsistent hybrid. | Post-rollback state doesn't match either the pre-rollback or the target state cleanly. | High | Transactional rollback (all-or-nothing), same principle as FM-14-015's migration rollback. | Restore from the last known-good checkpoint rather than attempting to patch the partially-rolled-back state. |
| **FM-15-024** | Missing events | An expected event never fires due to a publisher bug or a dropped message. | Expected downstream side effect never occurs despite the triggering condition being met. | Medium | At-least-once delivery guarantee on the event bus with acknowledgment tracking, per `docs/02-architecture/event-bus-specification.md`. | Detect via a reconciliation job comparing expected vs. actual state; re-emit the missing event if the trigger condition can be reconstructed. |
| **FM-15-025** | Duplicate events | Same event delivered more than once (common with at-least-once delivery semantics). | Subscriber receives two events with the same event ID. | Low | Idempotent event handlers keyed by event ID, expected given at-least-once delivery — this is a designed-for case, not a bug to eliminate at the bus level. | Deduplicate at the handler level using the event ID; no bus-level fix needed if handlers are properly idempotent. |
| **FM-15-026** | Events out of order | Events delivered in a different order than they were published, when ordering matters. | Handler logic that assumes causal order observes an effect before its cause. | Medium | Ordering guarantee per partition/key where causal order matters, or explicit sequence numbers the handler checks. | Buffer and reorder at the handler if sequence numbers are available; otherwise this indicates a bus configuration gap that needs fixing. |
| **FM-15-027** | Event storm | A feedback loop or a burst source causes an abnormally high volume of events in a short window. | Event throughput metric spikes far above baseline. | High | Rate-limiting/backpressure on event publication, with circuit-breaking for runaway publishers. | Identify and throttle/disable the runaway publisher; drain the backlog at a controlled rate rather than processing the full burst immediately. |
| **FM-15-028** | Infinite event loop | Handling event A causes publication of event B which causes republication of event A. | Same logical event chain repeats with growing or constant frequency indefinitely. | Critical | Cycle detection / max-hop-count on event causality chains (tracked via a correlation ID that increments a hop counter). | Break the loop by rejecting events beyond the max-hop ceiling; fix the handler logic that re-triggers the cycle. |
| **FM-15-029** | Subscriber failure | A subscriber crashes or errors while processing an event, and the event bus's handling of that failure is undefined. | Subscriber error rate spikes; unclear whether the event is retried, dropped, or lost. | Medium | Explicit failure policy per subscription (retry-with-backoff, dead-letter, or drop) declared and enforced by the bus, not left ambiguous. | Route failed events to a dead-letter queue for investigation rather than silently dropping or blocking the whole bus on one bad subscriber. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- Startup race conditions and partial initialization are the same failure at different granularities — a service that appears 'up' but has an uninitialized dependency will surface as a mysterious failure several layers away; always verify full readiness, not just process liveness.
- An event storm (FM-15-034) combined with subscriber failure (FM-15-035) can cascade into a full outage even if no single component crashed — treat event-bus backpressure as a first-class concern, not an afterthought.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
