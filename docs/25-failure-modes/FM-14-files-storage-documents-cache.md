# FM-14: Files, Storage, Document Processing & Cache

## Purpose

Everything that can go wrong persisting, reading, and caching data on disk.

## Scope & Related Documents

This file is part of `docs/25-failure-modes/`, the project-wide failure-mode catalog. It must be read alongside:

- `docs/13-devops/storage-layout.md` - `docs/13-devops/backup.md` - `docs/11-performance/caching.md` - `docs/07-observers/filesystem.md` - `docs/13-devops/persistence.md`

## Failure Catalog

Each failure is assigned a stable ID (`FM-14-0XX`) for cross-referencing from code comments, incident reports, and other failure-mode files.

| ID | Failure | Trigger Condition | Detection | Severity | Mitigation (prevent) | Recovery (respond) |
|---|---|---|---|---|---|---|
| **FM-14-001** | Missing file | Expected file was never created, or was moved/deleted by something outside NOVA's control. | File-existence check fails at the point of use. | Medium | Check existence before use, not just before write, and handle absence as a first-class expected case. | Regenerate/re-fetch the file if it's derivable; otherwise surface a clear 'file not found' rather than a cryptic downstream error. |
| **FM-14-002** | Locked file | Another process holds an exclusive lock on the file NOVA needs to read/write. | OS-level lock-conflict error on open. | Low | Retry with backoff for transient locks; detect and report persistent locks rather than retrying forever. | Wait with a bounded retry, then surface which process appears to hold the lock if detectable. |
| **FM-14-003** | Corrupted file | Partial write, disk error, or format mismatch corrupts a file. | Checksum mismatch, or format-specific parse failure on read. | High | Checksum on write for critical files; atomic write-then-rename pattern to avoid partial-write corruption. | Restore from the last valid backup per `docs/13-devops/backup.md`; never silently proceed with a corrupted file. |
| **FM-14-004** | Wrong encoding | File read/written with an incorrect character encoding assumption. | Garbled text on read, or downstream systems reject the written file. | Medium | Detect/declare encoding explicitly rather than assuming a system default. | Re-read with the correct encoding if the original bytes are still intact; otherwise the data may be unrecoverable — this underscores why encoding must be gotten right at write time. |
| **FM-14-005** | Duplicate filename | Two different files end up with the same target filename, causing an unintended overwrite or ambiguous reference. | Write operation targets a path that already exists with different content than expected. | Medium | Content-aware collision handling (versioned naming, or explicit overwrite confirmation) rather than silent overwrite. | Restore the overwritten file from backup if it was unintentional; establish a naming convention that avoids the collision going forward. |
| **FM-14-006** | Permission denied (files) | OS-level file permission blocks the operation. | Permission error on open/write. | Medium | Pre-flight permission check per FM-07-003's pattern, specific to filesystem operations. | Prompt for the specific permission/location change needed; never silently write to an unintended writable-but-wrong location as a workaround. |
| **FM-14-007** | Storage full | Disk/volume out of space. | ENOSPC on write. | High | Proactive free-space monitoring with alerts before hitting zero, especially before starting known-large operations. | Alert immediately; do not retry blindly since retrying won't succeed until space is freed. |
| **FM-14-008** | OCR skipped pages | Document-processing pipeline silently skips pages that fail OCR (blank scan, unusual orientation) without flagging the gap. | Extracted page count doesn't match source page count. | Medium | Verify extracted content count against source page/section count; fail loudly on mismatch rather than silently returning partial content as complete. | Re-run OCR on the specific failed pages with adjusted settings (rotation correction, higher DPI). |
| **FM-14-009** | Table extraction failed | Complex/merged-cell tables extracted incorrectly or dropped entirely. | Extracted structure doesn't match a spot-check of the source document's visible table structure. | Medium | Use a table-detection-aware extraction method, not generic text extraction, for documents flagged as containing tables. | Flag low-confidence table extractions for manual review rather than presenting them as ground truth. |
| **FM-14-010** | Markdown conversion incorrect | Source formatting (headings, lists, emphasis) lost or misapplied during conversion. | Rendered output visually diverges from source structure on spot-check. | Low | Use a well-tested conversion library and validate round-trip structure on a sample before trusting it for a new document type. | Flag conversion issues; fall back to a simpler text-only extraction if structural conversion is unreliable for that document type. |
| **FM-14-011** | Corrupted PDF parsing | Malformed or intentionally-obfuscated PDF structure breaks the parser. | Parser throws or returns empty/garbage content. | Medium | Use a robust parser with graceful degradation (attempt multiple extraction strategies) rather than failing hard on the first method. | Try an alternate extraction strategy (e.g. rasterize-and-OCR as a fallback) before declaring the document unreadable. |
| **FM-14-012** | Wrong language detection (documents) | Language-ID misclassifies the document, affecting downstream OCR/NLP quality. | Extraction quality metrics are poor in a pattern consistent with wrong-language processing. | Low | Cross-validate language detection against multiple signals (script, common words) rather than a single classifier pass. | Re-process with the corrected language setting once detected. |
| **FM-14-013** | Unsupported format | Document type NOVA has no extraction path for. | Format-detection step finds no matching handler. | Low | Fail explicitly and clearly for unsupported formats rather than attempting a best-effort parse that silently produces garbage. | Surface a clear 'format not supported' message; log frequency of unsupported formats to prioritize adding support. |
| **FM-14-014** | Database corruption | Underlying database file/index damaged. | Database integrity check fails on startup or query. | Critical | Regular integrity checks, WAL mode, and automated backups per `docs/13-devops/storage-layout.md`. | Restore from the most recent valid backup; replay any WAL entries since that backup if available. |
| **FM-14-015** | Migration failure | Schema migration fails partway, leaving the database in an inconsistent intermediate state. | Migration job exits non-zero, or schema-version check finds an unexpected intermediate version. | High | Transactional migrations (all-or-nothing) with a tested rollback path for every migration, per `docs/14-development/*`. | Roll back the partial migration using its rollback script; do not attempt to 'finish' a partially-applied migration by hand. |
| **FM-14-016** | Backup failure | Scheduled backup job fails or produces an unusable backup. | Backup job status check fails, or a periodic restore-test finds the backup unusable. | High | Regularly test-restore backups, not just verify the backup job 'completed', per `docs/13-devops/backup.md`. | Alert immediately and re-run the backup; investigate root cause before the next scheduled window. |
| **FM-14-017** | Restore failure | Backup exists but the restore process itself fails. | Restore job fails or produces data that fails integrity checks. | Critical | Periodic restore drills as part of standard operations, not just on-demand when actually needed in a crisis. | Fall back to an earlier backup generation if the most recent one fails to restore; escalate immediately since this indicates a systemic backup problem. |
| **FM-14-018** | Index corruption (storage) | Search/lookup index diverges from or is damaged relative to the source-of-truth data. | Query results are inconsistent with a direct scan of the source data. | Medium | Rebuild indices from source-of-truth data rather than trusting incremental index updates indefinitely without periodic verification. | Rebuild the affected index from source data; never treat the index itself as authoritative. |
| **FM-14-019** | Stale cache | Cached value not invalidated after the underlying data changed. | Cached value differs from a fresh read of the source. | Medium | Invalidate cache explicitly on every write path that changes the underlying data, in addition to any TTL. | Force invalidation and re-fetch; audit which write path missed the invalidation trigger. |
| **FM-14-020** | Cache miss explosion | Cache invalidated/cold all at once (e.g. after a deploy), causing a thundering-herd of simultaneous source lookups. | Source system load spikes sharply correlated with a cache-clear event. | Medium | Staggered/warmed cache population after a known cold-start event, plus request coalescing for identical concurrent misses. | Rate-limit source lookups during the recovery window; pre-warm cache proactively before known high-traffic periods. |
| **FM-14-021** | Cache poisoning | Bad/malicious data gets cached and served repeatedly until TTL or manual invalidation. | Cached value fails a sanity/validation check that a fresh value would pass. | Medium | Validate data before caching it, not just before using it, per FM-06-008's related pattern for context poisoning. | Purge the specific poisoned entry immediately; investigate how invalid data got past validation to be cached in the first place. |
| **FM-14-022** | Wrong invalidation | Cache invalidation logic clears the wrong key, or fails to clear the right one, due to a key-derivation bug. | Stale data persists despite an invalidation event having fired, or unrelated data is unexpectedly cleared. | Low | Deterministic, well-tested key-derivation logic with unit tests covering the invalidation mapping specifically. | Fix the key-derivation bug; force a broader cache clear as an immediate stopgap if the scope of the bug is unclear. |
| **FM-14-023** | Duplicate cache entries | Same logical value cached under two different keys due to inconsistent key normalization. | Two cache entries return semantically identical content for what should be one canonical key. | Low | Normalize cache keys consistently (case, whitespace, ordering) at a single shared point, not per-caller. | Consolidate to one canonical key going forward; not typically worth a retroactive cleanup unless memory pressure is a concern. |

## Compounding Failures

Notes on how failures in this file interact with failures elsewhere in this catalog — read these before assuming a bug is isolated to one subsystem.

- Cache poisoning (FM-14-021) combined with no invalidation-on-write path means a corrected value can be served stale indefinitely — every cache needs an explicit, tested invalidation trigger tied to the write path that changed the underlying data, not just a TTL.

## Severity Legend

- **Critical** — data loss, security compromise, or user-visible harm; requires an incident-response runbook, not just a bug ticket.
- **High** — silent incorrectness, significant user-visible breakage, or a failure that blocks task completion with no graceful degradation.
- **Medium** — degraded quality/UX or a failure with a working but imperfect fallback.
- **Low** — cosmetic, rare, or fully recoverable with negligible user impact.
