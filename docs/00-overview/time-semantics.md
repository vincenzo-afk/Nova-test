# Time Semantics

## Purpose

Specifies how NOVA handles time: which clock is authoritative for what
purpose, timezone handling, and clock-skew behavior — a gap that, left
unspecified, would let different components make inconsistent
assumptions about how to compare or order timestamps.

## Scope

Clock and timestamp conventions used throughout this repository's
schemas. Does not cover any single component's specific use of time
beyond the conventions here.

## Two distinct clock uses

- **Wall-clock time (UTC)** — used for anything a human reads or that
  must remain meaningful across a restart: every `timestamp` field in
  the message envelope (`docs/02-architecture/communication-model.md`),
  every memory record's recorded time (`docs/04-memory/timeline.md`),
  and every audit trail entry (`docs/10-security/audit.md`). Always
  stored and compared as UTC in ISO 8601 format; display-time conversion
  to the user's local timezone happens only at the UI layer
  (`docs/09-ui/`), never in stored data.
- **Monotonic clock** — used for anything measuring elapsed duration
  within a single running process: timeout enforcement
  (`docs/03-runtime/failure-recovery.md`), heartbeat intervals
  (`docs/03-runtime/service-lifecycle.md`), and lock-hold-duration
  tracking (`docs/03-runtime/resource-manager.md`). Never persisted
  across a restart and never compared against a wall-clock timestamp,
  since a monotonic clock has no fixed epoch relationship to wall-clock
  time.

## Why this distinction matters

Wall-clock time can jump (NTP correction, daylight saving transitions,
user manually changing system time) in ways that would corrupt a
duration measurement based on it — a timeout implemented by comparing
two wall-clock timestamps could fire early or never fire at all if the
system clock jumps during the timeout window. Monotonic time never jumps
backward and is unaffected by wall-clock adjustments, which is why every
duration-based mechanism in this repository (explicitly listed above)
uses it exclusively.

## Timezone handling

All persisted timestamps are UTC, with no exception — a record's
"local" time is always a display-time computation from UTC plus the
user's current timezone setting, never stored as a separate,
timezone-bound value that could become stale if the user travels or the
machine's timezone setting changes.

## Clock skew

Because NOVA is a single-machine, local-first system
(`docs/00-overview/non-goals.md`), cross-machine clock skew is not a
concern for the current v1 scope — all timestamps are generated by the
same machine's clock. This assumption is revisited if and when
multi-device synchronization (`ROADMAP.md` Phase 5) is undertaken, at
which point cross-machine clock skew becomes a real concern requiring
its own specification (e.g., a logical/vector clock or a synchronization
protocol) — explicitly out of scope now, consistent with
`docs/00-overview/assumptions.md`'s general principle of documenting
assumptions rather than pretending they don't exist.
